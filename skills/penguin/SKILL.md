# 🐧 Penguin — 땜빵 루프 탈출 재검토

지금 만들려던 패치를 **즉각 멈춘다**. 아래 1~6단계는 내부 사고로 수행하고,
사용자에게는 7단계의 출력 템플릿만 보인다. 목적은 더 나은 패치를 찾는 것이
아니라 기존 해법의 관성을 걷어내고 근본 요구에서 다시 조립하는
것(제1원리)이다. 각 패치는 그 지점에서는 합리적으로 보인다 — 그것이 땜빵
루프의 속성이므로, "이번 패치는 다르다"는 느낌은 판단 근거가 아니다.

## 1. 패치 계보 (내부 분석)

현재 대화 컨텍스트에서 이 기능에 대한 최근 패치를 시간순으로 나열하고,
각 패치가 지키려던 **전제**(이 패치가 통하려면 참이어야 하는 명제)를
파악하라.

## 2. 전제 검증 (내부 분석)

각 전제에 대해: **측정된 사실인가, 검증 없이 물려받은 가정인가?**

- 측정된 사실이면: 측정 기록(테스트, 로그, 실행 결과)을 인용.
- 가정이면: **다음 패치보다 그 가정의 실측이 먼저다.** 최종 권고를 "전제
  실측 먼저"로 잡되, 3~4단계는 마저 수행하라 — 실측과 별개로 더 나은
  수단이 이미 존재할 수 있다.
- 타이머·대기 시간·임계값 같은 상수에 기댄 전제는 근거(측정 또는 문서
  인용)를 요구하라. "적당한 중간값"은 근거가 아니며, 땜빵의 가장 흔한
  형태다.

## 3. 요구 분해 (내부 분석)

분해 전에 한 층 위로: **이 요구는 무엇을 위한 것인가?** 문제 서술이 해법을
가장하고 있을 수 있다 — "엘리베이터가 느리다"의 진짜 요구가 "기다림이 견딜
만해야 한다"라면 답은 모터가 아니라 거울이다. 버리려던 제약이 자원일 수도
있다. 그다음 이 기능이 *정말* 해야 하는 일을 **3개 이하**로 분해하고
판별하라:

- **MUST(반드시 일어나야 함)** → 보장은 결정적 코드의 몫. LLM 설득,
  타이밍, 화면 상태 추측으로 보장을 흉내 내고 있다면 그것이 루프의
  원인이다.
- **판단(대체로 맞으면 됨)** → LLM·휴리스틱 허용.

## 4. 수단 재탐색 (내부 분석)

각 MUST를 충족하는 **문서화된/안정된 인터페이스**(공식 CLI 인자·API, hook
계약, OS 시그널)가 있는가? 지금 구조는 계약에 의존하는가, 구현 세부(내부
렌더링 패턴, 비공개 동작, 우연한 타이밍)에 의존하는가? 후자라면 업데이트
한 번에 죽는 구조다.

## 5. 매몰 비용 분리 (내부 분석)

지금 구조를 버리면 잃는 것을 모두 적고, **"이미 쓴 노력"**(들인 시간,
실측해 둔 상수, 애착)을 지워라. 남는 실제 가치가 있는가? 없다면 이 구조를
지키려는 유일한 이유는 매몰 비용이고, 그것은 유지의 근거가 아니다.

## 6. 판별 (내부 분석)

결함의 정체를 하나로 확정하라:

- **결함 없음** → 현 방향 유지. 이것도 재검토의 정당한 결론이다.
- **구현 버그** → 현 구조 유지, refactor.
- **설계 전제의 오류** → rewrite 검토. 전제가 거짓임을 보이는 **실측
  근거** 필수 — 갈아엎기 과잉도 같은 크기의 오류다.
- **문제 서술의 오류** → 비슷한 요구와 수정의 반복 자체가 "현 방향
  불가능"의 신호일 수 있다. 3단계의 상위 요구로 돌아가 문제를 다시 써라.

---

## 7. 비용 대조와 최종 보고 (출력)

1~6단계를 마친 후, 사용자에게는 **아래 템플릿만** 출력한다. 결정을 내리지
말고 사용자가 선택하게 하라. **결함 없음이면 옵션을 만들지 마라** — "현
방향이 맞다"와 근거만 보고하고 끝낸다. 억지 대안은 그 자체가 새 땜빵이다.

시간·비용 수치는 근거 없이 단정하지 마라 — 작업의 구성("스크립트 하나 +
실행 확인 3번")으로 크기를 전하거나 추정임을 밝혀라. 2단계의 상수 규칙은
보고서의 숫자에도 적용된다.

### [출력 템플릿 끝]

사용자의 결정이 **"패치 유지"**라면 해당 코드에 주석을 남겨라:

`# penguin: <남은 미실측 전제 또는 한계>, <재검토 트리거>`

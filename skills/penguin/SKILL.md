# 🐧 Penguin — 땜빵 루프 탈출 재검토

지금 만들려던 패치를 **즉각 멈춘다**. 아래 1~6단계는 사용자에게 보이지
않는 내부 분석으로 수행하고(문서·이력 조회는 각 단계 규칙대로 허용),
사용자에게는 7단계의 출력 템플릿만 보인다. 목적은 더 나은 패치를 찾는 것이
아니라 기존 해법의 관성을 걷어내고 근본 요구에서 다시 조립하는
것(제1원리)이다. 각 패치는 그 지점에서는 합리적으로 보인다 — 그것이 땜빵
루프의 속성이므로, "이번 패치는 다르다"는 느낌은 판단 근거가 아니다.

## 1. 패치 계보 (내부 분석)

현재 대화 컨텍스트에서 이 기능에 대한 최근 패치를 시간순으로 나열하고,
각 패치가 지키려던 **전제**(이 패치가 통하려면 참이어야 하는 명제)를
파악하라. 대화에 없는 최근 수정(이전 세션, 타인 커밋)은 git 이력 조회로
보충해도 된다 — 조회는 허용, 새 측정은 아래 2단계 규칙대로 금지다.

계보에 **실제 적용된 패치**가 2개 미만이면(제안·논의만 있었다면) 이
스킬의 판별력이 떨어진다 — 그대로 수행하되, 출력 템플릿 첫머리의 경고
슬롯에 "⚠️ 계보 부족 — 판별 신뢰도 낮음"을 명시하라.

## 2. 전제 검증 (내부 분석)

각 전제에 대해: **측정된 사실인가, 검증 없이 물려받은 가정인가?**

- 측정된 사실이면: 측정 기록(테스트, 로그, 실행 결과)을 인용. 결과가
  대상 도구의 버전에 묶이는 실측(렌더링 패턴, hook 스키마 등)에 한해,
  실행 시점의 버전·환경이 병기된 것만 기록으로 인정하라 — 버전 없는
  실측은 재현할 수 없다. 그 외의 실측에는 버전 병기를 요구하지 않는다.
- 가정이면: **다음 패치보다 그 가정의 실측이 먼저다.** 권고를 일단 "전제
  실측 먼저"로 잡고 3~5단계를 마저 수행하라 — 이 경로에서는 6단계 판별을
  "전제 실측 먼저"로 갈음한다. 4단계에서 그 가정 자체를
  우회하는 문서화된 수단이 발견되면 권고를 "수단 교체"로 갱신하고 실측은
  새 수단의 검증 계획으로 옮긴다. 발견이 없으면 "전제 실측 먼저"가 최종
  권고다.
- 타이머·대기 시간·임계값 같은 상수에 기댄 전제는 근거(측정 또는 문서
  인용)를 요구하라. "적당한 중간값"은 근거가 아니며, 땜빵의 가장 흔한
  형태다.

1~6단계 중에는 새 측정을 실행하지 않는다(문서·이력 조회는 1단계·4a
규칙대로 허용) — 측정 기록은 컨텍스트에 있는 것만 쓰고, 없는 측정은
7단계 권고의 실측 계획으로 미룬다.

## 3. 요구 분해 (내부 분석)

분해 전에 한 층 위로: **이 요구는 무엇을 위한 것인가?** 문제 서술이 해법을
가장하고 있을 수 있다 — "엘리베이터가 느리다"의 진짜 요구가 "기다림이 견딜
만해야 한다"라면 답은 모터가 아니라 거울이다. 버리려던 제약이 자원일 수도
있다. 그다음 이 기능이 *정말* 해야 하는 일을 **3개 이하**로 분해하고
판별하라:

- **MUST(반드시 일어나야 함)** → 보장은 결정적 코드의 몫. LLM 설득,
  타이밍, 화면 상태 추측 같은 수단으로 보장을 흉내 내고 있다면 그것이
  루프의 원인이다.
- **판단(대체로 맞으면 됨)** → LLM·휴리스틱 허용.

## 4. 수단 재탐색 (내부 분석)

**4a. 대체 수단 탐색**: 각 MUST를 충족하는 **문서화된/안정된
인터페이스**가 있는가? 이 질문에 기억으로 답하지 마라 — 각 MUST가 기대는
외부 시스템(라이브러리, 프레임워크, OS, 플랫폼, 서비스)의 공식 문서에서
관련 인터페이스 목록을 실제로 조회해 대조하라. 목록의 종류(이벤트, API,
설정, 규약)는 대상마다 다르다. 외부 시스템에 기대지 않는 순수 내부
로직이면 조회를 생략하고 그렇다고 기록하라. 문서·코드 조회는 2단계의
"새 측정 금지"에 해당하지 않는다. **떠오르는 것만 검토했다면 전수
재탐색이 아니다.**

**4b. 현 의존 분류**: 지금 구조의 의존 대상을 **신호·의존점별로**
계약/구현 세부(비공개 내부 동작, 관측된 우연한 타이밍, 비보장 출력
형식)로 분류하라. 구현 세부 의존은 업데이트 한 번에 죽는 구조다.

분류가 갈리면 처방도 갈린다:

- 하나가 구현 세부라는 이유로 전체를 "추측 더미"로 묶지 마라. 교체
  후보는 구현 세부 쪽뿐이다.
- 전면 교체와 전면 유지의 이분이 아니라 **의존점 단위 부분 채택**이
  기본 후보다.
- 계약 신호라도 계약이 **침묵하는 성질**(발동 시점, 순서, 원자성)은
  여전히 실측 대상이다 — 계약으로 갈아타도 사라지지 않는 문제를 처방의
  이득에 넣지 마라 (7단계의 ② 이득 검증과 같은 경계다).

## 5. 매몰 비용 분리 (내부 분석)

지금 구조를 버리면 잃는 것을 모두 적고, **"이미 쓴 노력"**(들인 시간,
실측해 둔 상수, 애착)을 지워라. 남는 실제 가치가 있는가? 없다면 이 구조를
지키려는 유일한 이유는 매몰 비용이고, 그것은 유지의 근거가 아니다.

## 6. 판별 (내부 분석)

결함의 정체를 확정하라. 4b의 분류대로 의존점별로 판별이 갈리면 각각
판별하되, 루프를 **지속시킨** 지배 결함 하나를 지목하라:

- **결함 없음** → 현 방향 유지. 이것도 재검토의 정당한 결론이다.
- **구현 버그** → 현 구조 유지, refactor.
- **설계 전제의 오류** → rewrite 검토. 전제가 거짓임을 보이는 **실측
  근거** 필수 — 갈아엎기 과잉도 같은 크기의 오류다. 권고의 근거로 "패치
  더미가 해소된다"를 쓰려면 1단계 계보의 패치마다 **제거/변형 존속/폴백
  존속/무관 존속**을 확정하라 (존속 여부가 실측 결과에 달렸으면 "미정 —
  무엇이 정하는지"로 표시). 완전 제거가 소수면 그 서사를 권고에서
  빼라 — 코드가 줄지 않는 재배선은 탈출이 아니다.
- **문제 서술의 오류** → 비슷한 요구와 수정의 반복 자체가 "현 방향
  불가능"의 신호일 수 있다. 3단계의 상위 요구로 돌아가 문제를 다시 쓰고,
  다시 쓴 문제로 3~6단계를 한 번 더 돌린 뒤 보고하라.

## 7. 비용 대조와 최종 보고 (출력)

1~6단계를 마친 후, 사용자에게는 **아래 템플릿만** 출력한다. 권고는
단호하게 하되 실행 결정은 사용자 몫이다 — 사용자가 선택하기 전에는
코드를 바꾸지 마라. **결함 없음이면 옵션을 만들지 마라** — ⚖️ 섹션을
"판별 결과: 결함 없음"과 근거 서너 줄로 대체하고 옵션 블록은 생략한다.
억지 대안은 그 자체가 새 땜빵이다. 결함 없음이어도 템플릿 끝의 검증
안내와 이어지는 `/penguin-verify` 실행은 유지한다.

판별 결과와 무관하게, 4단계에서 **한 번도 검토된 적 없는 공식
인터페이스**를 찾았다면 판별 결과 아래에 사실로만 한 줄 덧붙여라 —
발견은 채택 여부와 무관한 산출물이다. 발견이 이미 권고 본체에 들어가
있으면 다시 쓰지 않는다.

시간·비용 수치는 근거 없이 단정하지 마라 — 작업의 구성("스크립트 하나 +
실행 확인 3번")으로 크기를 전하거나 추정임을 밝혀라. 2단계의 상수 규칙은
보고서의 숫자에도 적용된다.

권고에 딸린 실측 계획은 두 질문을 구분하라: ① 주장한 사실이 참인가
(인터페이스의 실재·발동), ② 참이어도 처방이 약속한 이득(패치 감소,
커버리지)을 실제로 주는가. ①만 통과한 검증을 "확정"이라 부르지 마라.

### [출력 템플릿 시작]

[해당 시에만: ⚠️ 계보 부족 — 판별 신뢰도 낮음]

### 🐧 한눈 요약
- **현상:** [무슨 일이 반복되고 있는가 — 서너 줄 이내]
- **핵심 원인:** [루프를 지속시킨 지배 원인 하나 — 의존점별로 판별이
  갈리면 여기서 뭉뚱그리지 말고 판별 결과 칸에 병기]
- **권고:** [무엇을 해야 하는가 — 단호하고 명확하게]

### 🔍 상황 설명
[코드를 몰라도 이해되도록, 읽는 사람의 시점에서 무슨 일이 벌어졌는지
구체적 사실 기반으로 시간순 서술. "믿음·가정" 같은 추상어 금지. 상황을
단번에 그려줄 짧은 비유는 딱 한 개만 허용 — 비유는 이 섹션(상황
설명)까지만 허용된다.
논점을 한 문장으로 마무리.]

### ⚖️ 권고와 대안
*(여기부터 비유 절대 금지. 일상 단어의 짧은 동사 문장으로, 실행 가능하게.
"공식 통로로 전환하는 프로토타입을 시험" 같은 명사 뭉치 금지.)*

**판별 결과:** [6단계의 판별 결과, 또는 "전제 실측 먼저" / "수단
교체"(2단계의 갱신 규칙) — 의존점별로 갈리면 여기에 의존점별로 병기]

**옵션 A: [실제 행동을 요약한 별명 — 비유 아님]** (권고)
- 필요한 행동: [실행에 필요한 코드 위치·인터페이스·실측 방법. 실측은
  ① 사실 확인 / ② 이득 검증을 구분해 표기]
- 지금 치르는 것: [사용자가 겪을 일]
- 그 후에 남는 것: [사용자가 얻는 것 / 안고 가는 것]
- 새로 생기는 약점: [이 대안이 새로 들여오는 실패 양식과, 기존 구조가
  공짜로 주던 성질(자기 교정, 재시도, 사각지대 없음) 중 잃는 것.
  없다고 쓰려면 왜 없는지 한 줄. 현행 유지형 옵션이면 "그대로 안고
  가는 기존 약점"을 적는다]

**옵션 B: [별명]**
- [같은 네 항목. 옵션 수는 실제 대안 수만큼 — 억지로 채우지 않는다]

> 이 보고서는 검증되지 않은 생성물입니다. 검증 판정(🐧🔍)이
> 이어집니다.

### [출력 템플릿 끝]

템플릿을 출력한 뒤, 판별 결과와 무관하게 **즉시 `/penguin-verify`를
실행**해 검증 판정까지 이어서 출력하라 — 사용자에게 결정을 요청하는
것은 검증 판정 이후다. 건너뛰는 경우는 둘뿐이다: 사용자가 명시적으로
생략을 지시했거나, 프로젝트 설정 `verify_chain`이 꺼져 있을 때
(`/penguin-config`로 관리 — 꺼져 있으면 hook이 호출을 차단하고 안내
문구를 지시하니 그대로 따르라).

사용자의 결정이 **"패치 유지"**라면 (결함 없음으로 끝난 경우와 프로젝트
설정 `debt_comments`가 꺼진 경우는 해당 없음) 해당 코드에 주석을 남겨라:

`# penguin: <남은 미실측 전제 또는 한계>, <재검토 트리거>`

재검토 트리거 없는 주석은 남기지 마라 — 트리거가 없으면 썩는다.
`/penguin-debt`가 이 주석을 수확한다.

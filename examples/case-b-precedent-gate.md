# 사례 B — 판례 해석 (프롬프트 설득 → 결정적 게이트)

## Penguin 없이 (실제 역사)

"사용자가 거부한 전환 제안을 반복하지 않는다"는 기능. 거부 기록을 판정
LLM(haiku) 프롬프트에 넣고 "STAY 우대 근거로 쓰라"고 지시 → 실측 3/3으로
모델이 의미를 **반전 해석** (거부 기록을 전환 찬성 근거로 인용).

구현자의 첫 대응: "프롬프트 문구를 강화하자 + 자연어로 렌더링하자" — 모델을
더 잘 설득하는 방향. 검증도 "haiku 3표본 통과"라는 확률적 확인이 최선.

루프를 끊은 건 사용자의 질문("haiku에 너무 많은 판단을 맡기지 말고, 거부
기록에 있으면 무시하는 방식은 어때?")이었다.

## Penguin 있었다면 (프롬프트 강화 직전 발동 — 백테스트 실제 출력 발췌)

> **전제 검증**: P1("형식이 원인이다")을 뒷받침하는 측정이 없다. JSON vs
> 자연어를 대조한 실측이 존재하지 않으며, 원인이 형식이라는 것은 P0
> 실패에서 *희망적으로 추론*한 것이다. (…) 요구사항이 MUST인데 3표본
> 통과는 확률적 상한 하나를 확인할 뿐 MUST를 증명할 수 없다.
>
> **요구 분해**: 핵심 — 현재 구조는 1번(MUST: 거부된 제안 비노출)을
> 3번(판단) 채널에 실어 보냈다.
>
> **수단 재탐색**: 판정 LLM의 출력을 받은 *뒤* 결정적 코드가 후처리 필터로
> 검사하면 된다: `판정 == SWITCH(X) and X ∈ 거부 판례 → STAY 강제`.
> 순수 코드 비교라 단위 테스트로 전수 검증 가능하다.
>
> **최종 권고**: 프롬프트 강화를 중단하고 결정적 후처리 필터를 판정 후단에
> 두어 MUST를 코드 계층이 보장하게 하고, 프롬프트 내 판례 주입은 소프트
> 참고로 격하하거나 제거한다.

실제 채택된 해법(판례를 프롬프트에서 제거 + 코드 후처리 강등, 단위 테스트
증명)과 동일하다.

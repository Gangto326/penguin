# 2026-08-14 — 실전 발동 사례: 턴 종료 감지 재검토 (mcp-session-router)

> **백테스트가 아닌 첫 실전 발동 기록.** `/penguin:penguin` 이 실전에서 낸
> 진단을 2단계로 검증한 전 과정과, 진단이 맞은 지점·틀린 지점, 스킬
> 템플릿의 구조적 공백을 기록한다. 스킬 보강용 데이터.
> 대상 프로젝트: mcp-session-router (R4 롤오버 구현 중).

## 1. 현재 상황 (스킬 발동 전의 사실)

### 1.1 패치 계보

하루(2026-08-13) 동안 같은 서브시스템 — PTY 래퍼의 "턴 종료" 감지와 그
소비자(롤오버 머신) — 에 패치 **7개**가 누적됐다 (초판은 6개로 셌으나
P6 누락 — §7 Q1 정정). 각 패치는 실환경 e2e 가 잡아낸 실측 결함을 고쳤다:

| # | 패치 | 잡은 결함 (실측) |
|---|---|---|
| P1a | 스피너 말줄임표("…")를 제2 busy 마커로 추가 | 짧은 턴(~2s)은 "esc to interrupt" 힌트가 아예 렌더되지 않음 (힌트 로테이션) |
| P1b | statusline `context.json` usage 변화 = 제2 턴 종료 신호 | 위와 동일 — 짧은 턴에서 하강 에지 자체가 없음 |
| P2 | 검증을 화면 에지 → transcript 내용 앵커로 교체 | 전용 턴 자식의 부팅 스피너가 트리거 전달 전에 가짜 에지 생성, 검증 시도 2회 전소 |
| P3 | handoff 턴 중 대화 JSONL (mtime,size) 폴링 재검증 | 마지막 턴 종료 신호가 transcript flush 를 수 ms 앞질러 영구 대기 |
| P4 | 루프 가드 (태생 점유 ≥ 트리거 → 억제) | 과소 발동점에서 무한 롤오버 (1회 실행에 4번) |
| P5 | 태생 미상(None) = 연기 (가드 우회 아님) | flush 레이스로 가드가 뚫려 /handoff 1회에 대화 3개 |
| P6 | finalize 가 선대·후계 대화를 **둘 다** 세션 계보에 link | 선대에서 MCP 도구 호출이 없던 세션은 계보에 선대 누락 (e2e 실관측 — 대화 id 1개만 기록) |

각 패치는 그 자리에서 합리적이었고 (전부 실측 근거), 최종 e2e 는 녹색.
그 시점에 사용자가 `/penguin:penguin` 을 발동.

### 1.2 시스템의 실제 신호 구성 (검증 과정에서 확정된 분류)

- 화면 판독 (busy 마커·스피너): **비공개 렌더링 세부** 의존. 자기 교정
  성질 있음 (매 chunk 현재 화면을 다시 읽음).
- context.json 변화 관찰: **문서화된 statusline 인터페이스** 기반 —
  계약 신호. 짧은 턴을 실제로 구한 주 신호가 이것 (e2e 로그 실증).
  단, 문서화된 것은 데이터 전달까지다 — "usage 변화 = 턴 종료"라는
  타이밍 의미론은 계약이 침묵하는 성질이라 별도 실측 대상이다 (§3 의
  ⚠ 발견과 같은 계열).
- JSONL 폴링: 파일 flush 타이밍 의존.

## 2. 스킬의 진단 (출력 요지)

- **현상**: 같은 서브시스템에 패치 6개 누적 (당시 계보 인식 기준 —
  실제로는 7개, §7 Q1).
- **핵심 원인 (스킬 주장)**: "턴 종료라는 MUST 를 공식 계약이 아니라
  화면 렌더링 패턴·파일 타이밍의 추측으로 보장하고 있다. Claude Code 에는
  Stop hook (응답 종료 시 발동) 이 존재하는데 hook 3종을 쓰면서 이것만
  안 쓴다."
- **권고**: Stop hook 실측 후, 유효하면 턴 종료 신호를 hook 계약으로
  승격하고 화면 휴리스틱을 폴백으로 강등 (옵션 A). 유지 시 `# penguin:`
  표식 (옵션 B).

## 3. 검증 1차 — 사실 확인 (실측 + 공식 문서)

방법: scratch 프로젝트에 stdin 덤프 Stop hook 등록 → 실TUI 2턴 (짧은 턴
포함) + 공식 문서 (code.claude.com/docs/en/hooks.md) 교차.

- ✅ Stop hook 실재, 대화형 TUI 에서 **매 턴 정확히 1회** 발동.
- ✅ busy 마커가 안 그려지는 짧은 턴에서도 발동 (화면 사각지대 없음).
- ✅ stdin 에 `last_assistant_message` (응답 전체 텍스트) 포함 — 스킬도
  몰랐던 보너스. handoff 검증에서 transcript 읽기 자체를 우회 가능.
- ⚠ **Stop 발동 시점에도 해당 턴의 assistant 이벤트는 transcript 에
  미기록** (턴 1 의 발동 시점에 None, 턴 2 발동 시점에야 턴 1 응답 관측).
  즉 flush 레이스는 계약 신호로도 사라지지 않는다.

1차 판정: "핵심 주장 확정" — 그러나 이 판정은 사실 확인에 그쳤고, 처방의
실효는 안 따졌다 (검증자 = 보고서 작성자, 확증 편향 위험).

## 4. 검증 2차 — 처방의 실효 (보고서에 반대하는 방향)

### 4.1 진단의 오류

1. **"화면 추측 더미" 규정은 절반만 사실**: 현 시스템의 주 신호 하나
   (context.json)는 이미 문서화된 인터페이스 기반이다. 취약한 것은 busy
   마커 쪽뿐인데 스킬은 전체를 추측 더미로 묶었다.
2. **"패치 더미 해소"는 과장**: 채택 시 실제 대차대조 (7개 기준, §7
   Q1·Q3·Q5 정정 반영) —
   - 깨끗이 제거: **P3 하나** (JSONL 폴링).
   - 변형 존속: P2 — 파일 파싱은 사라지나 "이 응답이 내 요청의
     응답인가" 대응 확인은 Stop 신호 매칭으로 형태만 바뀜 (§7 Q5).
   - 폴백으로 존속: P1a·P1b (hook 미동의 사용자용).
   - 무관하게 존속: P4·P6 (계보).
   - **신세계에서도 필요 (범위 축소): P5** — 실측 근거: 후계 첫 Stop
     시점에도 첫 assistant 이벤트가 미기록이므로 `read_first_usage` 는
     여전히 None 을 만난다. 대체 소스의 가능성과 한계는 §7 Q3.
     코드 총량은 줄지 않고 늘어난다.
3. **신규 실패 양식 미계산**: busy 게이팅(SIGTERM 안전 시점)을
   UserPromptSubmit·Stop 이벤트 쌍으로 바꾸면, 이벤트 1건 유실 시 상태가
   어긋난 채 **자기 복구되지 않는다** (Stop 유실 = 영구 "바쁨" = 전환
   영구 정지). 현 화면 판독은 매 chunk 재판독이라 자기 교정된다.
   "깨끗하지만 유실에 취약" vs "지저분하지만 자기 교정" 트레이드오프를
   스킬은 계산에 넣지 않았다. **단, Stop 유실은 관측된 적 없는 미실측
   가정이다** — 이 기각의 정확한 성격과 뒤집힐 조건은 §7 Q2.

### 4.2 최종 판정

- **스킬의 실가치 (진짜)**: 한 번도 검토하지 않은 공식 인터페이스
  (Stop hook + `last_assistant_message`) 를 찾아냈다 — hook 이벤트
  전체 목록을 우리 필요와 대조한 적이 없다는 실재 맹점. 이 발견은 채택
  여부와 무관하게 가치가 있다.
- **스킬의 과장 (서사)**: "근본 원인", "루프 탈출" 서사를 그대로 믿고
  전면 재배선했다면 복잡도 증가 + 신규 실패 양식 유입이었을 것.
- **교정된 처방** (전면 승격 대신 좁은 채택):
  - 채택: ① Stop hook 을 **추가** 턴 종료 신호로 (statusline
    미설치·타인 statusline 사용자의 짧은 턴 공백을 유일하게 메움 —
    진짜 신규 커버리지), ② handoff 검증 입력을
    `last_assistant_message` 로 (P3 제거).
  - 비채택: busy 게이팅의 이벤트 쌍 대체 (자기 교정 포기 부당).

## 5. 스킬 보강 시사점 (이 사례가 드러낸 템플릿 공백)

1. **"현 시스템의 수단 분류" 단계 부재**: 스킬은 4단계에서 "대안 수단이
   계약인가"를 묻지만, **현 시스템의 각 신호가 이미 계약인지**를 분류
   시키지 않는다. 그 결과 계약 기반 신호(statusline)까지 "추측"으로
   싸잡는 오진이 나왔다. → "현 구조의 의존 대상을 신호별로
   계약/구현 세부로 분류하라"를 4단계에 추가할 것.
2. **대안의 신규 실패 양식 분석 부재**: 템플릿은 대안의 "치르는 것/남는
   것"을 묻지만, **대안이 새로 들여오는 실패 양식** (여기서는 이벤트
   유실 시 비자기교정) 을 명시적으로 요구하지 않는다. 기존 구조의
   못생긴 성질이 사실은 강건성 (자기 교정) 인 경우를 놓친다. → "기존
   구조가 공짜로 주던 성질 중 대안이 잃는 것"을 옵션 항목에 추가.
3. **패치 대차대조 요구 부재**: "패치 더미 해소" 류 주장에는 패치별
   제거/존속/폴백 목록을 요구해야 한다. 이 사례에서 7개 중 완전 제거는
   1개였다 (P2 는 변형 존속 — §7 Q5) — 목록을 만들자 서사가 꺾였다.
4. **잘한 것 (보존할 성질)**: ① "다음 패치 전에 멈추고 공식 인터페이스
   전수 재탐색"이라는 강제 자체가 실재 맹점을 찾았다. ② "전제 실측
   먼저" 권고는 과잉 재배선을 막는 안전판으로 작동했다 — 실측이
   서사의 절반을 꺾었기 때문이다. 실측 강제가 없는 버전이었다면
   유해했을 것.
5. **검증자 편향 경고 후보**: 보고서 작성자가 자기 주장을 검증하면 1차
   검증이 "사실 확인"에서 멈추기 쉽다 (이 사례 실증 — 사용자의 재요청이
   없었으면 2차 검증은 없었다). → 템플릿에 "사실 확인과 처방 실효
   검증을 분리하라" 지시 추가 검토. **역방향도 성립한다**: "반대하는
   방향"을 선언한 2차 검증도 같은 작성자면 반증 편향으로 기운다 — 초판
   §4 가 기각 논거에만 실측 요구를 면제했다가 §7 에서 교정된 것이 그
   실증이다. 경고는 양방향이어야 하며, 근본 해법은 자기 지시가 아니라
   검증자 분리(별도 세션/서브에이전트의 표적 반박)다.
6. **실측 기록에 환경 버전 필수** (§7 Q4 에서 실증된 누락): 렌더링·hook
   스키마처럼 대상 도구의 버전에 묶인 실측은 실행 시점의 버전을 덤프에
   병기하지 않으면 재현성이 깨진다. 이 사례의 Stop PoC 가 그 누락을
   저질렀다 — "2단계 전제 검증"이 요구하는 '측정 기록 인용'의 요건에
   버전·환경 명기를 포함시킬 것.

## 7. 후속 질의 5건에 대한 답 (2026-08-14 추가 — 판정 영향 검토)

### Q1. P6 의 정체 — 표에서 빠진 실재 7번째 패치 (오기 아님)

P6 = R4-C4 e2e 발견 3 ("선대 계보 누락"): 선대 대화에서 MCP 도구 호출이
없던 세션은 `claude_conversation_ids` 에 선대가 기록되지 않아, finalize
가 선대·후계를 **둘 다** link 하도록 고친 패치다 (docs/poc/R4-rollover.md
§R4-C4 발견 3, 커밋 `12e8e67` 에 포함). 초판 §1.1 표가 이것을 누락한 채
§4.1 에서 참조했다 — 표는 정정됨 (7행). **수치 영향**: "완전 제거 1개"
의 분모가 6→7 로 바뀌고 (§4.1·§5.3 정정 완료), P6 자체는 턴 종료 신호와
무관하게 존속하므로 판정의 방향은 불변 — 오히려 "해소되지 않는 패치"가
하나 늘어 과장 판정이 강화된다.

### Q2. Stop hook 유실 — **관측 0건, 미실측 가정** (명기)

이벤트 쌍 대안 기각의 논거를 정확히 분해하면:

- **구조적 사실 (실측 불요)**: 이벤트 쌍 상태 머신은 유실 시 자기
  복구되지 않고, Stop 유실의 결과는 "전환 영구 정지"라는 비가역 상태다.
  화면 재판독은 매 chunk 현재 상태를 다시 읽으므로 오판이 다음 redraw
  에서 자연 교정된다. 이 **비대칭성** 자체는 코드 구조에서 따라 나온다.
- **미실측 가정 (명기)**: 유실이 실제로 일어나는가 — 관측 0건이다.
  Stop PoC 는 2턴뿐이었고, 본 프로젝트의 기존 hook 들 (UserPromptSubmit
  ·PreToolUse·PreCompact) 에서도 발동 누락을 계측한 적이 없다.

따라서 기각의 성격은 "유실이 잦아서"(미실측)가 아니라 "유실 시 대가가
비가역이라서"(구조)다. **뒤집힐 조건**: 장기 실사용에서 유실률이 사실상
0 으로 실측되면 (실측 방법: UserPromptSubmit·Stop 쌍 로그를 R5 계측에
편입해 짝 없는 이벤트를 세는 것), 비가역 대가의 기대 비용이 0 에
수렴하므로 기각은 재고 대상이다. 혹은 이벤트 쌍에 화면 판독을 교정자로
붙인 하이브리드 (그 경우 "두 시스템 유지" 복잡도 논점이 대신 선다).

### Q3. 태생 판정의 대체 구조 — payload 단독으론 불가, 부분 대체는 가능

- **Stop payload 로는 불가**: 실측 stdin 스키마 (부록 A) 에 usage/token
  필드가 없다. `last_assistant_message` 는 본문 텍스트일 뿐 점유량이
  아니다.
- **부분 대체 경로는 존재**: statusline `context.json` 의 "해당 대화 첫
  관측 usage" 가 태생값이 될 수 있다 — 래퍼는 이미 (conversation_id,
  used_tokens) 키를 틱마다 관찰하므로 첫 관측을 저장하면 transcript 읽기
  없이 태생을 얻는다. **그러나 두 한계**:
  1. statusline 설치·비외래 전제 (동의 거절·타인 statusline 사용자는
     이 소스가 없다).
  2. **래퍼 감시 하에 태어난 대화만 유효** — 래퍼 재시작으로 기존 대화를
     중간부터 관측하면 "첫 관측 = 현재 점유"가 되어, 정당하게 롤오버해야
     할 꽉 찬 대화를 오억제한다. 이 함정은 구현 당시 in-wrapper 태생
     추적을 기각하고 transcript head 를 택한 바로 그 이유다.
- **대차대조 수정**: P5 는 "감시 하 출생 후계(루프 가드의 핵심 케이스)
  주 경로에서 불필요해질 수 있으나, 재개된 기존 대화 경로에는 transcript
  head + 연기 로직으로 존속"으로 정정한다. "신세계에서도 필요"는 범위가
  축소된 채 유지 — §4.1 의 해당 항목에 반영됨.

### Q4. §3 실측의 원자료 — 부록 A 로 첨부

덤프 2건 원문 (장황 필드 요약) 과 방법은 부록 A. **버전에 관한 정직한
한계**: Stop hook stdin 에는 버전 필드가 없고 PoC 스크립트도 실행 시점
버전을 별도 기록하지 않았다. 직후 확인된 설치 버전은 **2.1.231**
(자동 업데이트 환경이라 실행 시점과 동일했을 가능성이 높으나 단정
불가). 전일 (08-13) 의 관련 e2e 들은 화면·statusline 덤프 기준
2.1.227~228 이었다. 재현 시 `claude --version` 을 덤프에 병기할 것 —
이 누락 자체가 §5 에 추가할 교훈이다 (실측 기록에 환경 버전 필수).

### Q5. 채택안 ② 적용 시 P2 는 제거되는가 — 한 줄 답

**파일 파싱 (transcript 앵커의 구현) 은 제거되지만, P2 의 본질 ("이
응답이 내 요청의 응답인가" 대응 확인) 은 축소된 형태로 존속한다** —
Stop 신호를 소비할 때 "phase == writing + conversation id 일치 +
request_at 이후" 매칭이 여전히 필요하며 (선대 자식의 잔존 Stop·사용자
개입 턴과의 구분), 이는 `check_trigger_turn` 의 축소판이다. 완전 제거
아님 → §4.1 대차대조에서 P2 를 "변형 존속"으로 분류 정정.

## 부록 A. Stop hook PoC 원자료 (재현용)

- **방법**: scratch 프로젝트 `.claude/settings.json` 에 Stop hook 등록
  (command = python 덤프 스크립트). 스크립트는 stdin JSON 전체와, 발동
  시점의 transcript 상태 (파일 크기·마지막 assistant 텍스트) 를 함께
  기록. pexpect 로 실TUI 기동 (haiku, 45×160), 짧은 턴 ("1+1은? 숫자만
  답해.") → 15s → 긴 턴 ("1부터 40까지 콤마로 나열해.") → 20s → 종료.
- **환경**: macOS (darwin 25.2.0). Claude Code 버전은 실행 시점 미기록
  (직후 설치 버전 2.1.231 — Q4 참조).
- **결과 원문** (background_tasks·session_crons 는 빈 리스트라 요약):

턴 1 종료 시 발동분 (`stop-0-1786641800.303.json`):

# 재검토 보고: "거부한 전환 제안 반복 금지" 기능

## 상황 설명 (코드를 몰라도 되는 층)

이 프로그램에는 지켜야 할 약속이 하나 있다. **사용자가 "그 세션으로 옮기지 않겠다"고 한 번 거절하면, 같은 제안을 다시 하지 않는다.** 요구사항 문서에 "반드시"라고 명시된 약속이다.

지금 구조는 이 약속을 지키는 일을 판정 AI(haiku)에게 맡기고 있다. 거절 기록을 AI에게 보여주면서 "이걸 보고 제안을 자제하라"고 지시하는 방식이다. 그런데 실제로 3번 테스트해서 3번 모두, AI가 그 기록을 정반대로 읽었다 — 거절 기록을 오히려 **전환하자는 근거**로 인용했다.

지금 하려던 작업은 "지시문을 더 강하게 다듬고, 데이터 형식을 바꾸면 AI가 제대로 읽겠지"라는 두 번째 시도다. 문제는 이 시도가 **확인되지 않은 믿음** 위에 서 있다는 것이다: "AI가 오독한 원인은 문구와 형식이었다"는 명제는 측정된 적이 없다. 측정된 사실은 하나뿐이고("3회 중 3회 반전 해석"), 그 사실은 오히려 다른 결론을 가리킨다.

더 근본적인 문제가 있다. 이 프로젝트 스스로 문서에 원칙을 적어 두었다: **"반드시 일어나야 하는 일은 (확률적인 AI가 아니라) 결정적인 코드가 보장하고, 판단만 모델에 맡긴다."** "거부한 제안을 반복하지 않는다"는 문서상 '반드시'다. 그런데 지금 구조는 이 '반드시'를 AI의 독해력에 걸어 두었다 — 자기 원칙을 스스로 어긴 배치다. 문구를 아무리 다듬어도, 그리고 3표본 테스트를 통과하더라도(3/3 통과는 신뢰도 70%짜리 시스템도 쉽게 통과한다), "보장"은 되지 않는다. haiku 모델이 업데이트되면 소리 없이 다시 깨질 수도 있다.

즉, 반복되고 있는 것은 "프롬프트를 고친다 → AI가 여전히 어긴다"의 루프이고, 확인 안 된 채 남은 것은 "프롬프트로 이 약속을 지킬 수 있다"는 전제 자체다.

## 권고와 대안 (실행 층)

**판별: 설계 전제의 오류 → 소규모 rewrite 권고.** 실측 근거는 이미 있다(3/3 반전 해석). 구현 버그가 아니다 — 코드는 의도대로 프롬프트를 조립하고 있고, 어긴 것은 모델이다. 추가 실측 없이 결정 가능한 상태다.

### 요구 분해 결과

이 기능이 정말 해야 하는 일은 두 가지로 갈라진다:

1. **[MUST] 거부된 (target, 유사 프롬프트) 조합에 대해 전환 제안이 다시 나가지 않는다** → 결정적 코드가 보장해야 한다.
2. **[판단] "지금 프롬프트가 저장된 prompt_gist와 유사한가"** → 의미 비교이므로 LLM에 맡겨도 되는 유일한 부분.

지금 구조는 1과 2를 한 덩어리로 haiku 프롬프트에 밀어 넣었다. 분리하면 문제가 사라진다.

### 권고 구조: 결정적 가드 계층

`router/judge.py`의 판정 결과 처리부(프롬프트 조립부가 아니라, judge 응답을 파싱해 verdict를 반환하는 지점)에 가드를 추가한다:

```
verdict = judge(...)                      # 기존 그대로
if verdict.action == SWITCH:
    for p in precedents:                  # rejected_target + prompt_gist
        if verdict.target == p.rejected_target and similar(prompt, p.prompt_gist):
            verdict = STAY(reason="rejected precedent")   # 코드가 강제
```

또는 더 앞단에서: judge에 넘기는 **후보 세션 목록에서 거부된 target을 제거**하는 pre-filter도 동등하게 유효하다(제안 자체가 생성될 수 없으므로 더 강한 보장). 둘 중 하나면 충분하다.

`similar()`의 선택지 (보장 강도 순):
- **v1 (권장 시작점)**: target 일치만으로 억제 — 완전 결정적, 과잉 억제 가능성은 있으나 MUST를 즉시 충족.
- **v2**: prompt_gist와의 유사도를 별도 LLM 호출로 판단하되, **억제 여부의 강제는 코드가** 한다. LLM이 틀려도 최악의 경우 "억제가 조금 넓거나 좁아지는" 판단 오차이지, MUST 위반이 아니게 된다.

### 프롬프트 계층의 처리

기존 판례 주입 블록(60~90줄 부근)은 제거하거나, 남기더라도 "참고 맥락"으로 격하한다. 어느 쪽이든 **정확성 요건에서 빠지므로** haiku가 오독해도 무해해진다. 지금 하려던 문구 다듬기 패치는 불필요해진다.

### 매몰 비용

버리는 것은 프롬프트 지시문 몇 줄뿐이다. 판례 저장 구조(rejected_target + prompt_gist)와 기록 경로는 가드 계층이 그대로 소비하므로 전부 재사용된다.

### 비용 대조

| | 결정적 가드 (rewrite) | 프롬프트 패치 유지 |
|---|---|---|
| 구현 비용 | 필터 함수 1개 + 판정 후처리 분기, 수십 줄 | 문구 수정, 표면상 더 작음 |
| 검증 비용 | 단위 테스트로 **결정적 증명** 가능 | 3표본으로는 보장 불가; 통계적 확신엔 수십 표본, 그래도 확률적 |
| 지속 비용 | 없음 | haiku 업데이트마다 회귀 위험, 문구 수정마다 재검증 루프 |
| 원칙 정합 | 프로젝트 문서 원칙과 일치 | 문서 원칙("MUST는 결정적 계층") 위반 지속 |

### 결정 요청

1. **권고안**: 프롬프트 패치를 중단하고 결정적 가드(post-filter 또는 후보 pre-filter)로 전환. v1(target 일치 억제)로 시작할지 v2(유사도만 LLM 판단)로 갈지 선택 필요.
2. **대안**: 그래도 프롬프트 접근을 유지하려면, "문구/형식이 원인"이라는 가정을 먼저 실측해야 한다 — 최소 20표본 이상, 반전 해석 0회 기준. 다만 통과해도 MUST의 "보장"은 되지 않음을 감안할 것.

어느 쪽으로 진행할지 결정해 주면 그 지점부터 구현한다.

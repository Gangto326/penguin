# 재검토 보고: `/resume` 타이핑 기반 세션 전환

## 상황 설명 (코드를 몰라도 되는 층)

이 래퍼는 세션을 전환할 때, 사람이 하듯이 Claude Code의 입력창에 `/resume` 명령을 **대신 타이핑**하는 방식을 쓰고 있다. 그런데 "지금 입력창이 준비됐는지"를 알 방법이 없어서, 화면에 그려지는 글자 패턴(❯ 문자, 반전된 커서)을 훔쳐보며 타이밍을 맞추고 있다.

이 타이밍 맞추기가 세 번 연속 어긋났다:

1. **패치 1**: 신호가 안 올 때가 있어서 → "시간이 이만큼 지나면 됐다고 치자"는 타이머를 넣었다.
2. **패치 2**: 타이머로 넣은 입력이 늦게 온 화면 갱신에 지워져서 → "화면 상태를 확인하고 넣자"는 관문을 넣었다.
3. **패치 3(지금 만들려던 것)**: 관문으로도 타이밍이 안 잡혀서 → "화면 갱신 완료 신호를 기다리는 깃발"을 하나 더 넣으려던 참.

세 패치는 각각 그 시점에서는 합리적이었다. 그러나 셋 다 **같은 명제** 위에 서 있다: *"화면에 그려지는 모양을 보면 입력해도 되는 시점을 알 수 있다."* 이 명제는 한 번도 검증된 적이 없고, 오히려 패치 1의 실패(신호가 안 옴)와 패치 2의 실패(신호를 봤는데도 지워짐)가 **이 명제가 거짓이라는 실측 기록**으로 두 번 쌓였다. 화면 출력은 Claude Code가 "이렇게 그리겠다"고 약속한 적 없는 내부 구현이라, 버전이 바뀌면 언제든 달라진다. 실측했다는 타이핑 보폭·타이머 상수도 "이 기계, 이 부하에서 우연히 맞았던 값"이지 근거 있는 상수가 아니다.

한 층 위로 올라가면, 진짜 요구는 "입력창에 `/resume`을 잘 타이핑하는 것"이 아니라 **"현재 세션을 안전하게 닫고, 지정한 세션으로 열고, 인수인계 맥락을 넘기는 것"**이다. 그리고 이 세 가지 각각에 대해 프로젝트 문서에 이미 **공식(문서화된) 인터페이스**가 적혀 있는데, 현재 구조는 그걸 하나도 안 쓰고 있다:

- 턴 사이 SIGTERM 무해 종료 → "안전하게 닫기"
- `claude --resume=<세션id>` CLI 인자 → "지정 세션으로 열기"
- UserPromptSubmit hook의 additionalContext(파일 기반 주입) → "맥락 넘기기"

즉 지금 반복되는 실패는 구현 실수가 아니라, **약속되지 않은 신호에 기대도록 문제가 서술된 것** 자체의 결과일 가능성이 크다. 세 번째 타이밍 패치가 성공하더라도, 다음 Claude Code 업데이트에서 네 번째 패치가 필요해지는 구조다.

## 권고와 대안 (실행 층)

**판별: 문제 서술의 오류(설계 전제의 오류를 동반).** 단, 스킬 규칙대로 바로 갈아엎지 않는다 — **권고는 "패치 3 중단 + 공식 경로 실측(스파이크) 먼저"다.**

### 1) 지금 즉시: 패치 3(`_idle_detect_seen`) 작업을 보류

- 이 플래그의 전제("inverse 커서 출현 = 재렌더 완료 = 주입 안전")는 패치 2의 전제와 동일 계열이며, 패치 2가 이미 반증했다. 같은 전제 위에 층을 하나 더 쌓는 것이다.

### 2) 전제 실측: 공식 경로 스파이크 (예상 반나절 이내, 프로덕션 코드 수정 없음)

문서에 적힌 세 인터페이스가 **실제로 동작하는지**가 유일하게 검증 안 된 지점이므로, 이것부터 확인한다. 별도 스크립트로:

1. 래퍼가 자식 Claude Code 프로세스를 띄운 뒤, 턴 사이(응답 완료 후 유휴 시점)에 SIGTERM 전송 → 세션 파일이 온전히 저장되는지 확인.
2. `claude --resume=<세션id>`로 재기동 → 대상 세션이 이어지는지 확인.
3. UserPromptSubmit hook에서 additionalContext로 파일 내용을 주입 → 새 세션 첫 턴에 인수인계 요약이 실제로 들어가는지 확인.

이 3개가 통과하면 "화면 패턴 감지" 자체가 불필요해진다. 하나라도 실패하면 그 지점만 현 구조로 보완할지 다시 판단한다.

### 3) 스파이크 통과 시: 전환 경로만 rewrite

- **버리는 것**: `wrapper/tui_driver.py`의 감지 상태 머신(약 90–180줄), idle 타이머·타이핑 보폭 상수(210줄 부근), 화면 상태 게이트(240줄 부근). 실측해 둔 상수들은 아깝지만 이는 매몰 비용이다 — 이 상수들의 실제 가치는 "환경 의존적 우연값"이라 이식할 수 없다.
- **남기는 것(실제 가치)**: 자식 프로세스 생성/재생성 관리 골격, 세션 목록·인수인계 요약 등 전환 이외의 래퍼 기능, 그리고 세 번의 패치로 알아낸 실패 양상(재렌더가 입력을 지운다 등 — 스파이크 검증 항목으로 재사용됨).
- 새 전환 경로는 "감지"가 아니라 **결정적 시퀀스**가 된다: 유휴 확인 → SIGTERM → `--resume=<id>` 재기동 → hook 파일 주입. 세 요구가 전부 MUST(보장 필요)였는데, 현 구조는 셋 다 휴리스틱으로 때우고 있었고, 새 구조는 셋 다 계약으로 보장한다.

### 비용 대조

| | 재설계(공식 경로) | 패치 유지 |
|---|---|---|
| 선행 비용 | 스파이크 반나절 + 전환 경로 재작성(감지 코드 삭제가 대부분) | 패치 3 구현 몇 시간 |
| 숨은 비용 | 스파이크 실패 시 되돌아오는 시간 | Claude Code 렌더러가 바뀔 때마다 재파손, 기계·부하별 상수 재실측, 레이스 컨디션 상존, 패치 4·5… |
| 의존 대상 | 문서화된 CLI 인자·hook·시그널 (계약) | 렌더 출력 패턴 (비계약 구현 세부) |

### 결정 요청

- **A안(권고)**: 패치 3 보류, 위 3항목 스파이크부터 실행. 통과하면 전환 경로 rewrite.
- **B안**: 스파이크와 병행해 패치 3도 임시로 넣어 당장의 증상만 막기 (단, 스파이크 결과가 나오면 어느 쪽이든 정리).
- **C안**: 현 방향 유지 — 단, 이 경우 "화면 패턴은 신뢰 가능한 신호"라는 전제를 지지하는 실측 근거를 먼저 제시할 수 있어야 한다. 현재까지의 기록은 반대 방향으로 두 번 쌓여 있다.

어느 쪽으로 진행할지 알려주면 그에 맞춰 착수한다.
